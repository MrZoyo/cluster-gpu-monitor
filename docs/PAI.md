# PAI 监控

简体中文 | [English](PAI.en.md) | [文档目录](README.md) | [项目首页](../README.md)

PAI 模块展示阿里云 PAI 配额、节点、DSW/DLC 任务、用户用量和利用率曲线。独立采集进程
通过云 API 读取数据并写入 `pai.db`；Web 只读本地快照，刷新页面不会调用云 API。

## 默认关闭

不创建 `config/pai.toml`，或保持 `enabled = false`，即可使用原有裸金属监控。
此时没有 PAI 导航或双入口首页，`/api/pai/*` 返回普通 404，手动访问 `#/pai...` 会回到总览。
配置缺失或无效也不会注册 PAI 路由。修改启用状态后须重启 Web。

启用后，根页面显示裸金属和 PAI 两个入口，`#/baremetal` 为裸金属总览。既有的集群、主机、
GPU 和用户排行链接继续有效。两类资源的身份和统计口径不同，页面不合并两边的数据。

## 启动

先完成 [README 快速开始](../README.md#快速开始)，准备 Web 所需的 inventory、settings 和
裸金属数据库。另行安装并配置 PAI CLI；适配器已在官方 CLI v1.0.1 及使用该引擎的 `pai-tui`
包装器上验证。`cli_path` 可指向任一兼容可执行文件。采集器使用文件锁，支持 Linux/macOS。

1. 复制 [pai.example.toml](../config/pai.example.toml) 为私有 `config/pai.toml`。
2. 填入账号、地域、工作空间和根配额，设置 `enabled = true` 和正确的 `cli_path`。
3. 在采集进程的 CLI 身份中配置只读权限。凭证不写入 TOML、源码或网页。
4. 先执行一轮采集，再启动常驻采集器和 Web。两个进程使用相同的配置/数据根。

```sh
export GPUMON_ROOT=/absolute/path/to/runtime
export GPUMON_PAI_CONFIG="$GPUMON_ROOT/config/pai.toml"

uv run python -m gpumon.pai.collector --once
uv run python -m gpumon.pai.collector
# 另一个终端设置相同的两个环境变量，再启动 Web
uv run gpumon web --host 127.0.0.1 --port 8848
```

每轮先通过 STS 核实账号；账号不匹配时停止本轮，不继续读取其他资源。采集需要读取配额、
节点、Pod、任务、用户用量、DLC 任务详情和 CloudMonitor 指标。上线前应在专用身份下验证
这些读取权限。Feature 归属另需 `paiworkspace:ListMembers` 和 `paiworkspace:ListConfigs`，
通过 `aiworkspace` 2021-02-04 接口查询；`ListConfigs` 只请求 `CommonQuotaConfig` 分类。
两次查询按拓扑周期缓存，在任务/指标采集后运行，共享每轮超时、调用次数与分页上限，
只保存用户 ID 和候选 Quota ID；失败保留旧快照但不用于归属，不影响原始任务用量积累。
验证通过不等于证明该身份没有其他权限；本模块不执行写操作探测。
接口参考：[ListMembers](https://help.aliyun.com/zh/pai/developer-reference/api-aiworkspace-2021-02-04-listmembers)、
[ListConfigs](https://help.aliyun.com/zh/pai/developer-reference/api-aiworkspace-2021-02-04-listconfigs)。

## 配置

相对 `db_path` 以 `GPUMON_ROOT` 为基准。默认读取该根目录下的 `config/pai.toml`；
`GPUMON_PAI_CONFIG` 可指定其他位置。未知配置字段会校验失败。

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | 显式启用；开启时账号、工作空间和配额必填 |
| `region` | `cn-hangzhou` | 云资源所在地域 |
| `account_id` / `workspace_id` / `quota_id` | 空 | STS 账号、工作空间、要监控的根配额 |
| `cli_path` / `profile` | `pai-tui` / 空 | CLI 路径和身份配置名；CLI profile 中的凭证优先于环境变量 |
| `db_path` | `data/pai.db` | 独立 PAI 数据库，不与裸金属共用 |
| `baremetal_notice` | 空 | 启用 PAI 后可在裸金属页面显示的说明文字 |
| `ranking_timezone` | `Asia/Shanghai` | 周界、页面时间及 CSV 使用的 IANA 时区 |
| `ranking_week_start` | `monday` | 每周第一天，英文小写 `monday` 至 `sunday` |
| `ranking_reset_time` | `00:00` | 本地时区的每周换榜时刻，24 小时制 `HH:MM` |
| `poll_interval_s` / `degraded_interval_s` | `120` / `180` | 正常及连续失败后的采集间隔 |
| `topology_interval_s` / `stale_after_s` | `300` / `600` | 配额/节点目录缓存周期及普通来源陈旧阈值 |
| `request_timeout_s` / `round_timeout_s` | `12` / `100` | 单次 CLI 调用与整轮时间预算 |
| `max_calls` / `concurrency` | `120` / `2` | 每轮最大调用数与并发数；小规格宿主可用单路并发 |
| `max_pages` / `max_workloads` / `max_nodes` | `8` / `32` / `64` | 分页、任务指标和节点数量边界 |
| `metric_window_s` / `retention_hours` | `600` / `24` | 重叠回读窗口及原始指标保留时间 |
| `host_metric_interval_s` | `240` | 任务 CPU/内存利用率的刷新周期 |
| `job_refresh_s` / `queued_job_refresh_s` | `21600` / `600` | 运行中/排队 DLC 任务详情缓存周期 |
| `max_job_details` | `8` | 每轮最多刷新多少个 DLC 详情 |

节点两种 Pod 视图和 GPU 指标优先采集；任务详情、CPU/内存和成员归属按上次尝试时间公平刷新。
可选来源超出剩余预算时延后，`round.deferred_sources` 列出来源，`round.complete=false`；旧值继续按新鲜度判断。
主动延后不等于云接口失败，实际调用和分页仍受同一硬预算限制。

连续两轮失败后降低采集频率，两轮成功后恢复正常。遇到限流停止新请求并至少等待 600 秒，
连续限流继续退避。超出调用或分页预算时标记失败、保留最近成功值，不把部分结果当完整覆盖。
各字段范围的事实来源为 [PaiSettings](../src/gpumon/pai/config.py)。

## 页面与数据口径

| 页面 | 内容 |
| --- | --- |
| 总览 | 配额分配、物理卡热力图、低利用率提醒、排队任务及来源健康 |
| 配额 | 根配额与子配额卡片：分配构成、可调度节点、运行任务、用户、节点计算均值和逐卡微缩条；配额详情汇总绑定节点、任务（含父配额任务与闲时借用）、用户及本周统计 |
| 节点 | 逐卡映射、所属配额、健康状态及任务下钻 |
| 任务 | 搜索/筛选/排序，申请与调度资源、提交策略、单 Pod 规格及近 1 小时曲线 |
| 用户 | Owner / 提交者名下任务、配额内和闲时资源、用量差异 |
| 排行 | 默认本周 Feature / Quota 排行；可切用户、上周和原有滚动窗口，导出 CSV |

- 卡数按节点和卡号去重；父配额包含子配额，不能相加。申请量、调度量、配额分配和物理卡映射分别展示。
- 每个节点分别查询默认 Pod 视图和 `OversoldTypes=ForceQuotaOversold` 闲时视图，合并后按任务、Pod 和卡号去重。
  已确认的闲时占用显示任务、用户、Pod 和 GPU 卡号；两种视图独立记录来源状态，失败时保留旧值并标注陈旧。
  参数拼写来自 [ListNodePods](https://help.aliyun.com/zh/pai/developer-reference/api-paistudio-2022-01-12-listnodepods)，
  与任务提交策略 `ForceQuotaOverSold` 的大小写不同。节点 `RequestGPU` 仍保留平台普通请求口径，不与闲时映射重复累计。
- 物理卡仅在 Pod 指标 GPU 索引集合与物理 `GPUIndexes` 一致时关联；多任务共享卡或关联不明时保留未知。
- “已分配 GPU”使用运行任务的调度 GPU 总数（缺少调度量时回退申请量），包含借用一次。
  同一卡片以紫色显示“其中借用 × 卡”；热力图的“已定位占用”仅表示已取得物理映射的部分。
- 热力图区分物理分配与实测计算：只有节点、任务及两种 Pod 视图新鲜、一致且无未定位运行任务时，确认未分配的卡才显示 `0`。
  已定位借用卡显示对应任务；指标卡号与物理卡号不能可靠关联时，利用率仍为未知。
  查询失败、来源陈旧、节点请求量不一致或任务未完整定位时，未映射卡显示 `?`，不按空闲补零。
  原配额优先，借用任务被回收后释放资源并重新排队；能否调度还取决于节点健康、CPU、内存和配额策略。
- `UseOversoldResource` 标识已调度任务实际使用的闲时资源，与提交策略和配额共享开关不同。
  常规任务详情未显示节点不代表无法查询；以显式闲时 Pod 视图为准。闲时任务卡数不与物理卡总数相加。
- 排队提示结合提交策略、配额容量和单 Pod 规格，保留平台原始原因。数据不足时不宣称一定无法调度。
  总览排队列表默认收起，摘要保留任务总数、风险数量和前两项任务；展开后查看完整列表，后台刷新保留展开状态。
- 利用率曲线按源时间保留任务/Pod/GPU 维度，使用固定 120 秒桶；迟到点可修订已有桶，缺测不计零。
  未关联物理节点的任务仍可展示指标，历史曲线不回填当前物理归属。
- 首页和总览的“计算均值（任务）”按运行任务各 GPU 的最新新鲜计算指标取平均，每张卡等权，
  包含未关联物理节点的闲时任务；未占用卡、缺测和陈旧值不参与。它不是各任务均值的等权平均。
- “集群 GPU 利用率（估算）”将监控工作空间的运行任务单卡计算之和除以物理池总卡数，包含池内借用。
  只在任务列表/拓扑新鲜、任务单卡指标完整、数量不超物理容量、无已知重复映射且没有运行集合外的占卡任务时提供；不是全池逐卡实测值。
  尚未定位的借用任务可能占用未映射卡，这些卡不能按空闲 0% 计入逐卡均值。
  首页和总览的指标卡常驻显示数值或简短原因，例如“8 张卡保存中”“2 张卡缺指标”。
  详细公式、完整阻断原因和数据完整度通过悬停、键盘聚焦或触屏点击说明入口查看。
  数值仍由后端计算；前端仅依据同一 API 快照解释空值，不补零、不降低完整性要求。
  陈旧映射只提示上次占用状态，不声称对应任务当前仍在保存或停止。
- 任务和用户详情页可保留上次成功取得的陈旧指标，并明确标注；总览的任务平均只使用新鲜指标。
- 低利用率提醒使用近 10 分钟计算均值，至少 5 个分钟点；陈旧值保留显示，但不参与提醒。
  CPU/内存利用率为任务 Pod limit 的百分比，申请量另列。
- 个人归属来自 RAM Owner / 提交者，不使用 CloudMonitor 的主账号 `userId`，也不识别共享容器内的逐进程使用人。
- GPU·小时只用当轮成功读取、状态为 Running 的任务累计。长间隔最多计两倍降级周期，已知调度量为零时保留零。
  按 UTC 小时汇总，保留 32 天；非整点边界按小时桶重叠比例估算。这是观测估算，不是计费账单。

- 配额页按两种口径同时归入任务：提交到该配额（含子配额）的任务，以及实际跑在该配额绑定节点上的任务，每个任务只计一次，并标注“父配额任务”或“借出给闲时任务”；借用方向固定为“借入 / 借出”。
  配额详情的本周统计复用排行接口的 Feature 行（根配额用其单列行），同一时间窗 10 分钟内不重复请求；排行读取失败只影响该区块。
  总览、任务表、节点详情和用户表中的配额名均可进入配额详情。页面在总览与各面板中把口径说明收进默认折叠的“统计口径”。

### Feature 周排行

默认按北京时间（Asia/Shanghai）周一 00:00 至今统计；上周是前一个完整配置周。
时区、每周第一天和换榜时刻均可配置。
滚动窗口仍保留，PAI 的时间窗和维度选择独立于裸金属页面，并在自动刷新时保留。
直接提交子 Quota 的任务归属该 Feature。直接提交根配额（如 `training`）的任务，额外通过
任务 `UserId` → 工作空间成员 `Roles` → `CommonQuotaConfig.allowedRoles` 归入唯一匹配的
子 Quota。不按用户名猜测；管理员等 `PAI.*` 通用角色和根 Quota 的角色不代表 Feature。
无匹配、多 Feature、成员/配置读取失败、分页不完整或快照陈旧时，保留为根配额未归属量。

根配额在独立区域展示且不参与排名：任务用量仍为根配额**直接提交量**，同时给出已归属与
未归属 GPU·小时；配额容量/用量计数仍来自平台，可能包含子配额。Feature 用量拆分为直接提交和
根配额归属两部分。两处存在重叠，不能相加；页面汇总使用后端 `totals`，每份任务用量只计一次。
借用 GPU 时间、计算指标、CPU/内存时间及任务数随归属一起计入 Feature，借用仍是总占用的子集。

**历史按当前角色重算**：现有数据库没有历史角色关系，所有窗口均使用最新有效的成员映射。
角色变化后，历史窗口的 Feature 分布可能改变；原始提交 Quota、任务历史和用户总量保持不变。
`feature_attribution` 返回依据、快照时间和新鲜度；`users[].quotas` 仍表示原始提交配额。

在已升级版本的私有 `config/pai.toml` 中配置：

```toml
ranking_timezone = "Asia/Shanghai"
ranking_week_start = "monday"
ranking_reset_time = "00:00"
```

例如配置 `America/New_York`、`sunday`、`06:30`，表示纽约时间周日 06:30 开始新一周。
修改后下一次排行请求按新周界查询已有历史，不清空历史。这里设置每周换榜时刻，
页面每 120 秒自动刷新及采集频率仍分别沿用原设置。
应用前可校验：`GPUMON_ROOT=/path/to/runtime uv run python -c
'from gpumon.pai.config import load_pai_settings; load_pai_settings(); print("PAI config OK")'`。
不存在的时区、非法星期或时间格式会被拒绝；先升级到支持这些字段的版本再添加配置。
IANA 时区数据使用系统数据或随依赖安装的 `tzdata`。

夏令时按本地日历计算，因此一周可能有 167 或 169 小时。若换榜时刻因夏令时跳过，
按跳变时差向后顺延（如 02:30 → 03:30）；若重复出现，取第一次。
API 的 `timezone`、`week_start`、`reset_time` 及 CSV 元数据说明实际周界，页面与导出使用同一时区。

历史仍按 UTC 小时汇总。若周界未对齐 UTC 整点（含半小时时区），边界小时中的资源秒及
指标和/计数按重叠时长比例分摊，使相邻窗口合计守恒；无法还原小时内部的启动、停止或缺测分布，
任务数包含重叠小时内出现的任务。API 和 CSV 用 `boundary_estimate=true` 标记这一估算。
正在积累的当前小时不会再次折减。默认周界对齐 UTC 整点，统计口径保持原样。

- **任务 GPU·小时**包含常规和池内借用；借用是总占用的子集。根配额任务可额外归入唯一匹配的 Feature，全局合计只计一次，不向父配额重复累计。
- **当前配额 / 用量 / 占用率**来自最新 Quota 快照，始终表示当前值，即使选择上周也不会变成历史值。
  快照陈旧时显示提示。资源上实际分配及祖先配额任务占用卡数可在用量提示中查看，不能当作该 feature 的任务用量。
- **窗口配额占用率**为观测到的 Quota 用量卡秒除以同一时间段的容量卡秒，配额变更按时长加权。
  使用平台 `gpu_used`，该记账计数可能不含池内借用。父配额用量可含子配额，容量和用量均不可跨层级相加。
  缺失、零容量或没有历史分母时占用率未知，不以当前容量倒算历史。
- **占用期间计算效率**为有效计算 GPU 时间除以有指标的占用 GPU 时间，并显示占用时间的指标覆盖率。
  它与“占用了多少配额”不同，不能把占用率视为计算效率。
- 配额历史从这次功能上线后首次观测开始累计，使用前一轮快照积分（配额目录约 5 分钟刷新）。
  首次观测不回填，失败快照不延续；长间隔最多累计两倍降级周期。资源池的观测覆盖率显示在汇总中，
  个别配额与资源池明显不同时在该行单独标注。
  部分覆盖时，占用率仅代表已观测部分，任务历史可能更长。保留 32 天，小时边界精度与任务排行相同。
- 页面先给出本窗口汇总：占用 GPU·小时合计（全局去重）、集群 GPU 利用率估算、占用期间计算效率、当前池内任务占用和活跃 Feature（用户维度为活跃用户）。
  “接近满额”（窗口配额占用率 ≥ 90%）和“计算偏低”（有指标的占用期间计算效率 < 10%）只是提示，不改变排序。
  归属规则、历史重算依据和观测分母收进默认折叠的“统计说明与数据详情”；成员归属更新时间明确标注报表时区。
- Feature 用量条中实色为直接提交，描边浅色为从根配额归入，点击 Feature 整行即可展开两项 GPU·小时及覆盖时间、分母，名称旁箭头支持 Tab、Enter 和空格；根配额与排行同表但单独成组、
  无名次，未归属量保持可见，具体原因收进详情。借用画在条下紫色细条，与主条同尺度，是总量的子集。
  同一行内的拆分按显示精度对齐合计，精确值见 CSV。成员角色陈旧或读取失败时，归属数值显示“—”，
  标题旁标注“归属降级”，简短异常提示始终可见，可点“查看详情”；排序提示改为“临时排序：仅按直接提交 GPU·小时”。
  常态说明不占据排行上方，汇总卡保留核心数值和覆盖率。展开状态在维度切换与自动刷新后保留。
- **导出 CSV**包含窗口、生成时间、任务历史起点、截断标记以及当前返回的全部行。
  Feature 导出包含容量 GPU·小时、用量 GPU·小时、观测小时、应观测小时、已排除不存在小时、
  覆盖率口径和计算指标，供周报核查。
  未知值留空；CSV 不触发自动汇报或发送消息。

页面每 120 秒在后台刷新，保留滚动、筛选和展开状态；输入搜索词时推迟刷新。
请求期间保留当前页面，成功后更新变化的数值和行，图表复用实例并保留图例选择。
请求失败时保留上次成功数据并提示陈旧，后续刷新成功后自动解除提示。
前端版本检测独立运行：发现新资源版本时提醒用户重载，不自动重载；原有脚本、样式加载失败的
重载兜底提示继续保留。来源列表展示每项数据的
获取时间、源采样时间及失败类别。采集失败不代表云节点宕机，“未见占用”也不等于可立即调度。
节点异常提示只提供处理指引，页面不会重启 DSW、终止 DLC 或修改云资源。

## 自有资源池借用与审计

本项目在 2026-10-10 按云服务方确认的自有资源池口径修正闲时统计：

- `UseOversoldResource` / oversold / 超卖在这里表示临时借用其他 Quota 暂不需要的节点。
  借用不新增物理 GPU 容量，也不引入额外 GPU 资源费用；不能将借用卡数加到集群总卡数上。
- 节点和卡号可由显式闲时 Pod 查询确认；未取得可靠映射时保持未知，不据此猜测出借团队。原 Quota 始终有更高优先权，
  需要资源时借用任务暂停、释放资源并重新等待。不能把这描述成有额外计算池或一定永久终止。
- 借用消耗的 GPU 时间计入**借用任务的提交团队/个人**。Feature 由子 Quota 直接提交或根配额任务的当前成员角色归属，
  用户仍由 RAM Owner/提交者归属；根配额直接提交单列且不排名。它不是对出借团队的时间归账。
- 原有 Quota API 的 `gpu_used`/`occupancy_pct` 继续作为**配额记账计数**，可能不含借用。
  这个计数不能替代集群物理占用或计算利用率。

审计分别回答：

1. **占用多少 GPU 时间**：`gpu_hours` 是成功观测的运行任务调度 GPU 数 × 时间，包含借用一次；
   调度量缺失时沿用申请量估算。`borrowed_gpu_hours` 是其中借用的子集，旧 `oversold_gpu_hours` 为兼容别名，
   不能把别名再加一次。排队/暂停不累计；已观测暂停或失败后的恢复若无可信新调度时间，从恢复观测后再计。
2. **占用期间计算效率**：每卡计算样本代表 60 秒，用小时汇总里的样本数估算已测 GPU 时间，
   `measured_gpu_hours = min(占用 GPU·小时, 计算样本数 / 60)`。
   `effective_gpu_hours` 为这段已测时间按计算利用率加权后的 GPU 时间；
   `hardware_efficiency_pct = effective_gpu_hours / measured_gpu_hours × 100`。
   `gpu_metric_coverage_pct` 同时给出有指标的时间占总占用时间的比例。缺测不计零，也不把一两个样本外推到整小时。
   旧 `compute_mean` 保留样本均值；审计界面使用新的 GPU 时间加权效率。GPU 忙碌百分比不是 FLOPS 或训练吞吐效率。
3. **某段时间的集群整体计算利用率**：新 `cluster` 历史按每轮观测积分，自有物理池容量只计一次。
   `task_utilization_estimate_pct` 是同一有效观测段内的工作空间任务有效计算 GPU 时间 / 物理池容量 GPU 时间；
   `task_occupancy_pct` 是同段任务占用 GPU 时间 / 容量 GPU 时间。包含借用，但不增加容量分母。
   该估算仅覆盖配置工作空间；外部工作空间的未公开任务不在其分子中，不能声称全租户逐卡实测。
   `task_estimate_coverage_pct` 是有效观测时间占所选窗口的比例，页面与 CSV 同时给出。

集群历史从本次启用审计统计后累计，保留 32 天，不用当前容量回填以前的时段。
`physical_utilization_pct` 仅在全部物理卡的状态/计算都可确认时返回；
无法定位的借用卡在计算统计中保持未知；热力图可显示原配额空闲的 `0`，但不补零到统计。
`physical_metric_coverage_pct` 表示可确认的容量时间比例。
窗口中的集群估算与团队/个人指标可能有不同的覆盖区间，比较时必须同时查看覆盖率。
CSV 带 `cluster_*` 元数据和逐行占用/借用/效率/指标覆盖字段，供同一窗口周报核查。

### 配额时间覆盖率

配额时间覆盖率为 `observed_quota_hours / expected_quota_hours × 100%`。应观测时长等于所选
时间窗减去**成功、完整的配额采集确认该配额不存在的时长**（`absent_quota_hours`）。
删除期间不参与分母，也不会补成观测时长或零容量记录；整个窗口均确认不存在时，覆盖率为未知值。
配额存在但容量或用量缺失时仍计缺测。采集失败、长时间中断和升级前没有存在性证据的
时段也保留在分母，不因当前快照中没有这个 ID 而推断整段历史不存在。

采集器将完整配额列表的有效时间和各 ID 的存在时间分别累计，沿用 `max_gap` 限制；
失败会打断连续性。后来新建的配额也能排除此前完整快照已确认的不存在时段。
旧库未增加存在性历史时继续使用原窗口分母。历史修复须有单独证据，可在
`quota_absence_override` 写入不与新采集重叠的小时级排除记录，并保留原因和备份。
这些排除记录不会改变任务 GPU·小时、配额容量或配额记账占用率。

例如，24 小时窗口内有 8 小时确认配额不存在、15 小时有效观测，覆盖率为
`15 / (24 - 8) = 93.75%`。其余 1 小时仍是缺测，不补成观测或零容量。
API 的 `quota_coverage_basis` 为 `window_excluding_known_absence`；配额详情及 CSV
同时保留 `observed_quota_hours`、`expected_quota_hours`、`absent_quota_hours` 和百分比
`quota_coverage_pct`。整个窗口确认不存在时，分母为零、覆盖率返回 `null`，页面显示“—”。

删除重建会产生不同 Quota ID，系统不会仅因名字相同而自动合并历史。人工合并前应核对
工作空间、父配额和时段，备份原数据，并同步核对用量、容量及存在性历史，避免重复计算。
没有历史存在性证据的时段不能根据当前名称或容量反推；有证据的停用期只从覆盖率分母排除。

一个用户可以拥有多个 Feature 的访问角色。直接提交到子配额的任务始终按任务 `QuotaId`
统计；提交到根配额的任务只有在当前角色唯一匹配一个 Feature 时才额外归入该 Feature。
多重匹配保留在根配额的未归属用量，并标记 `multiple_features`，不均分或重复计数。
根配额的这项归属使用当前角色，角色变化可能改变历史窗口的展示，不是任务运行时角色快照。
同一 UserId 的多配额用量仍汇总到同一个用户，并保留各提交配额明细；同名但不同 UserId
不会自动合并。多个角色若最终只匹配同一个 Quota ID，也不属于多重 Feature 匹配。

## 生产部署

通用发行包提供采集模块，**不会自动安装云 CLI、创建账号或启用 PAI 服务**。仓库现有 systemd
和 Compose 服务负责裸金属监控；PAI 需要部署方单独配置采集服务及 CLI。部署时应：

- 为 PAI 配置独立无登录服务账号，固定 CLI 版本和校验和。凭证只注入采集进程；Web 无法读取。
  使用环境变量时，确认 CLI profile 不会覆盖专用身份。
- 准备独立数据目录，通过共享组给 Web 读取权限。采集器 UMask 为 0027，新目录/数据库通常为
  0750/0640；现有目录权限须单独检查。长期写连接维护 WAL/SHM，避免只读访问失败。
- 按宿主容量设置服务内存、CPU、进程数和请求上限；用至少一个完整采集周期测量实际消耗。
  配置上限、整轮墙钟时间和实际 CPU/内存占用是不同指标。
- 分别备份裸金属和 PAI 数据库，使用 SQLite 在线备份。升级后重启独立采集服务；回滚到不含 PAI 的
  旧代码时停止 PAI 采集并保留数据库、配置和凭证。
- 使用带认证的 HTTPS 入口。PAI API 不加入匿名 GPU 摘要，也没有“每个用户只能看自己”的应用内 RBAC。
